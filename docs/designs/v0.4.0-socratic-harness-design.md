# v0.4.0 Socratic Harness Design

## Status

Design approved for planning. Do not implement directly from this document without a separate implementation plan.

## Goal

Turn Idea Harness from a principle-oriented clarification skill into a strict, practical, Socratic requirements harness for small app ideas.

The skill should help a non-programmer move from a vague idea to two usable outputs:

- A user-facing requirements brief that makes the first version clear.
- A coding-agent execution prompt that is tightly bounded by a harness gate.

## Non-goals

This version will not:

- Choose a tech stack.
- Design architecture.
- Generate code.
- Expand into business model, growth, operations, pricing, or full product planning.
- Ask exhaustive PRD-style questionnaires.
- Accept vague answers just to reach `Ready` faster.

## Requirements Engineering Basis

The flow should borrow the practical spine of software requirements engineering without exposing heavy process language to ordinary users.

Relevant source ideas:

- ISO/IEC/IEEE 29148 frames requirements engineering as the set of processes that produce requirements for systems and software across the life cycle.
- SWEBOK treats software requirements as a knowledge area covering requirements definition, elicitation, analysis, specification, validation, and review.
- IREB CPRE emphasizes identifying and documenting requirements from sources, conflict resolution, and validating requirements against stakeholder needs.

For Idea Harness, these map into a lightweight sequence:

1. Elicit the real problem.
2. Identify users and stakeholders.
3. Analyze context and boundaries.
4. Specify functional and data needs.
5. Validate with non-goals and acceptance criteria.
6. Gate the output so downstream agents cannot add unconfirmed work.

## User Experience Principle

The skill should be strict, not warm.

Strict means:

- It points out unclear answers plainly.
- It does not accept "all of them" as a V1 answer.
- It does not move to Ready while any required gate is missing.
- It challenges broad feature requests by asking which one matters first.

Strict does not mean:

- Using jargon.
- Asking many questions at once.
- Making the user write a full requirements document.

The interaction should feel like a sharp product coach with a checklist, not a brainstorming assistant.

## Socratic Question Rules

Every `Need More Info` turn must follow these rules:

1. Ask one question only.
2. The question must expose one real requirement fork.
3. Prefer 2-4 choices.
4. Choices must represent meaningful tradeoffs, not a random menu.
5. Include a recommendation and explain why it is the smallest useful V1.
6. If the user says "all", ask which one comes first for V1.
7. If the user says "you decide", choose a recommendation but require confirmation.
8. If the user gives a vague answer, ask a narrower follow-up.
9. If answers conflict, ask only about the conflict.
10. Do not ask about implementation details unless a requirement cannot be clarified without them.

Example style:

```markdown
## 下一步
你现在最想先摆脱哪种麻烦？

A. 每天不知道该先做什么
B. 重要截止日期容易忘
C. 资料和笔记太乱
D. 学了多久、有没有坚持不清楚

推荐：先选 A。它最容易收成一个很小的第一版：打开后只告诉你今天该做什么。
```

## Fixed Clarification Gates

`Ready` requires all seven gates below. Missing any gate means `Status: Need More Info`.

### 1. Problem / Pain

What concrete pain is the app trying to remove?

The skill must not accept:

- "I want a website."
- "I want an app."
- "I want something for learning."

It must push toward:

- What is messy, slow, forgotten, repeated, or hard today?
- What specific pain should V1 solve first?

### 2. User / Stakeholder

Who will actually use it, and who judges whether it works?

For small apps, this is often:

- Just me.
- My family.
- My students.
- My customers.
- Me as admin and others as viewers.

If there are multiple user types, V1 must name the primary one first.

### 3. Context / Scenario

When and where does the user open it? What is happening before and after use?

This prevents vague features from becoming an oversized product.

### 4. One V1 Job

What one job must V1 complete?

The skill should force one main job before supporting features. If the user lists multiple jobs, ask which one is first.

### 5. Data Behavior

What information is entered, shown, and retained?

Use plain language:

- "下次打开还要不要看到之前内容？"
- "这些内容是只存在这一台设备，还是换设备也要有？"
- "别人需要看到各自不同的内容吗？"

The skill must not infer accounts, cloud sync, databases, or backend storage unless the user confirms the need in ordinary language.

### 6. Non-goals / Constraints

What must V1 explicitly not do?

Default forbidden assumptions should include unconfirmed:

- Account login.
- Admin dashboard.
- Payment.
- Notifications.
- AI features.
- Analytics.
- Sharing.
- Multi-user permissions.
- Import/export.
- Cloud sync.
- Mobile app packaging.

The skill should convert broad "later" features into V1 non-goals.

### 7. Acceptance Criteria

How will the user know V1 works?

Acceptance criteria must be checkable actions or visible results. Avoid vague terms like "simple", "nice", "smart", or "easy" unless converted into observable behavior.

## Ready Rules

The skill may output `Status: Ready` only when all gates are confirmed:

- Problem / Pain
- User / Stakeholder
- Context / Scenario
- One V1 Job
- Data Behavior
- Non-goals / Constraints
- Acceptance Criteria

The skill must stay at `Need More Info` when:

- A required gate is missing.
- The user says "all of them" for V1.
- The user delegates a requirement decision with "you decide" but has not confirmed the recommendation.
- There is a conflict between answers.
- A requested feature implies login, backend, payment, notification, multi-user behavior, or AI behavior that has not been confirmed.
- Acceptance criteria are not testable.

## Need More Info Output

`Need More Info` should become more diagnostic than the current version.

Template:

```markdown
## 当前结论
Status: Need More Info
Reason: ...

## 已确认
- ...

## 仍缺
- Gate: ...
- Why it matters: ...

## 不能先假设
- ...

## 下一步
...

A. ...
B. ...
C. ...

推荐：...
```

Rules:

- `仍缺` must name the missing gate.
- `Why it matters` should explain the downstream guessing risk.
- `不能先假设` should block the most likely wrong implementation.

## Harness Gate Semantics

### Must Build

Only confirmed V1 behavior goes here.

### Must Not Build

Confirmed non-goals and likely overreach go here.

### Allowed Assumptions

Allowed assumptions must be low-risk and implementation-neutral, such as:

- Use clear labels.
- Keep the UI simple.
- Use sensible empty states.

Do not allow assumptions such as:

- Add login.
- Store data in the cloud.
- Add AI recommendations.
- Add analytics or reports.

### Forbidden Assumptions

This is the hard fence. The execution prompt must explicitly forbid anything the user has not confirmed but a coding agent might be tempted to add.

## Example Flow

Input:

```text
我想做一个学习管理网站。
```

First response should not ask for tech stack, login, database, or full feature list.

It should ask:

```markdown
## 当前结论
Status: Need More Info
Reason: "学习管理网站"只是形式，不是问题。现在最容易跑偏的是先管理哪种学习麻烦。

## 已确认
- 你想做一个学习管理相关的网站。

## 仍缺
- Gate: Problem / Pain
- Why it matters: 不知道先解决哪种麻烦，下一步 agent 很容易脑补课程表、任务看板、笔记库或统计面板。

## 不能先假设
- 不能假设需要登录、课程表、任务系统、笔记库、统计图表或数据库。

## 下一步
你现在最想先摆脱哪种学习上的麻烦？

A. 每天不知道该先学什么
B. 作业或截止日期容易忘
C. 资料和笔记太乱
D. 学了多久、有没有坚持不清楚

推荐：先选 A。它最容易收成一个很小的第一版：打开后只处理今天该做什么。
```

## Test Strategy

Smoke tests should cover:

1. Vague idea stays `Need More Info` and asks for Problem / Pain.
2. User says "all of them" and skill forces V1 priority.
3. User says "you decide" and skill asks for confirmation of recommendation.
4. All seven gates confirmed results in `Ready`.
5. Ready output includes Harness Gate and Execution Prompt.
6. Ready output does not introduce login, backend, payment, AI, analytics, or sync unless confirmed.
