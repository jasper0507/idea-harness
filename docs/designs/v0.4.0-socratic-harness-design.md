# v0.4.0 苏格拉底式 Harness 设计

## 状态

设计已确认，可进入实现计划阶段。不要直接按本文实现，下一步应先写单独的实现计划。

## 目标

把 Idea Harness 从“原则型澄清 skill”改成一个严格、实用、苏格拉底式的小应用需求控制器。

新版 skill 要帮助非程序员把一句模糊想法推进到两个层次的产物：

- 默认给用户看的极简需求澄清输出，减少压力和 token 消耗。
- 内部给 agent 使用的严格控制结构，用 Harness Gate（控制门）限制范围，并在用户明确要求时生成执行 Prompt。

## 不做什么

v0.4.0 不做这些事：

- 不选择技术栈。
- 不设计技术架构。
- 不生成代码。
- 不扩展到商业模式、增长、运营、定价或完整产品规划。
- 不做厚重 PRD 式问卷。
- 不为了更快 `Ready` 而接受模糊回答。

## 需求工程依据

新版流程要借鉴软件工程需求分析的实用骨架，但不把沉重术语暴露给普通用户。

参考思想：

- ISO/IEC/IEEE 29148 把需求工程视为一组贯穿系统和软件生命周期的需求过程。
- SWEBOK 把软件需求作为知识域，覆盖需求定义、获取、分析、规格化、验证和评审。
- IREB CPRE 强调从需求来源识别和记录需求，处理冲突，并验证需求是否符合利益相关者需要。

映射到 Idea Harness 后，流程应简化为：

1. 追问真实问题。
2. 明确用户和利益相关者。
3. 分析使用场景和边界。
4. 规格化功能需求和数据需求。
5. 用不做什么和验收标准验证范围。
6. 用控制门限制下游 agent，防止添加未确认内容。

## 交互原则

新版 skill 的语气应严格，不走温和陪聊路线。

严格意味着：

- 直接指出回答哪里不清楚。
- 不接受“都要”作为第一版答案。
- 任何必需门槛缺失时，都不能进入 Ready。
- 遇到宽泛功能诉求时，必须追问第一版先解决哪一个。

严格不意味着：

- 使用专业黑话。
- 一次问很多问题。
- 逼用户写完整需求文档。

交互气质应像一个带清单的严格产品教练，而不是发散型头脑风暴助手。

## 输出原则：内部严格，外部极简

v0.4.0 的输出要分成两层：

- **内部层**：严格维护七个澄清门槛、缺口判断、禁止假设、Harness Gate 和执行 Prompt 生成规则。
- **用户层**：默认只展示用户需要继续推进的信息，避免把内部审计过程暴露给普通用户。

默认情况下：

- `Need More Info` 只展示 `已确认` 和 `下一步`。
- `Ready` 只展示 `需求简报`。
- `Harness Gate` 不直接展示。
- `执行 Prompt` 不直接展示。

只有用户明确要求“生成执行 Prompt”“给我可以交给 Codex/Claude Code/Cursor 的 prompt”“下一步让 AI 实现”时，才额外输出执行 Prompt。

这样做的目的：

- 降低用户心理压力。
- 减少每轮输出 token。
- 保持界面清爽。
- 让 harness 控制留在内部，不打扰普通用户。
- 仍然防止下游 agent 添加未确认功能。

## 苏格拉底式提问规则

每个 `Need More Info` 回合都必须遵守这些规则：

1. 每次只问一个问题。
2. 问题必须揭示一个真实需求分叉。
3. 优先给 2 到 4 个选项。
4. 选项必须代表有意义的取舍，不能只是随便列菜单。
5. 必须给推荐选项，并说明为什么它是最小可用第一版。
6. 如果用户说“都要”，必须追问第一版先要哪一个。
7. 如果用户说“你决定”，可以给推荐，但必须要求用户确认。
8. 如果用户回答模糊，下一轮必须继续缩小问题。
9. 如果用户答案冲突，只问冲突点。
10. 除非需求无法澄清，否则不要问实现细节。

示例风格：

```markdown
## 下一步
你现在最想先摆脱哪种麻烦？

A. 每天不知道该先做什么
B. 重要截止日期容易忘
C. 资料和笔记太乱
D. 学了多久、有没有坚持不清楚

推荐：先选 A。它最容易收成一个很小的第一版：打开后只告诉你今天该做什么。
```

## 固定澄清门槛

`Ready` 必须满足以下七个门槛。缺任何一个，内部状态都必须保持 `Need More Info`。

### 1. 问题 / 痛点

必须明确这个小应用要移除的具体麻烦。

skill 不能接受这类表述：

- “我想做一个网站。”
- “我想做一个 App。”
- “我想做一个学习相关的东西。”

skill 必须把用户推向更具体的问题：

- 现在什么地方乱、慢、容易忘、重复或难处理？
- 第一版先解决哪一个具体麻烦？

### 2. 用户 / 利益相关者

必须明确谁真的会打开它用，以及谁判断它有没有用。

小应用里常见情况包括：

- 只有我自己。
- 我的家人。
- 我的学生。
- 我的顾客。
- 我作为管理者，其他人作为浏览者或填写者。

如果有多类用户，第一版必须先确认主用户。

### 3. 使用背景 / 场景

必须明确用户在什么时候、什么情况下打开它，以及使用前后发生什么。

这个门槛用来防止一个模糊功能扩散成过大的产品。

### 4. 第一版主动作

必须明确第一版只完成哪一个主要动作。

skill 要强制先确定一个主动作，再谈辅助功能。如果用户列出多个动作，必须追问第一版先做哪个。

### 5. 数据行为

必须明确输入什么、显示什么、保存什么。

用普通话表达：

- “下次打开还要不要看到之前内容？”
- “这些内容是只存在这一台设备，还是换设备也要有？”
- “别人需要看到各自不同的内容吗？”

除非用户用日常语言确认了相关需求，否则 skill 不得推断账号、云同步、数据库或后端存储。

### 6. 不做事项 / 约束

必须明确第一版不做什么。

默认应阻止这些未确认假设：

- 账号登录。
- 后台管理。
- 支付。
- 通知。
- AI 功能。
- 数据分析。
- 分享。
- 多用户权限。
- 导入导出。
- 云同步。
- 打包成手机 App。

用户提到“以后再说”的功能，应转成第一版不做事项。

### 7. 验收标准

必须明确怎样算第一版能用。

验收标准必须是可检查的动作或可见结果。不要接受“简单”“好看”“智能”“好用”这类泛词，除非已经转成可观察行为。

## Ready 规则

只有七个门槛都确认后，skill 才能进入内部 `Ready` 状态：

- 问题 / 痛点
- 用户 / 利益相关者
- 使用背景 / 场景
- 第一版主动作
- 数据行为
- 不做事项 / 约束
- 验收标准

遇到以下情况，必须保持 `Need More Info`：

- 任一必需门槛缺失。
- 用户对第一版说“都要”。
- 用户说“你决定”，但还没有确认推荐方案。
- 已有答案之间存在冲突。
- 某个功能暗含登录、后端、支付、通知、多用户或 AI 行为，但用户没有确认。
- 验收标准不可检查。

## Need More Info 输出

`Need More Info` 的内部判断要严格，但用户可见输出必须极简。

用户可见模板：

```markdown
## 已确认
- ...

## 下一步
...

A. ...
B. ...
C. ...

推荐：...
```

内部规则：

- 内部仍要判断当前缺的是哪一个门槛。
- 内部仍要记录为什么这个门槛重要。
- 内部仍要维护不能先假设的内容。
- 用户可见输出不要展示 `Status`、`Reason`、`仍缺`、`为什么重要`、`不能先假设`。
- 如果用户答案冲突，可以在 `下一步` 中直接指出冲突并只问冲突点。

## Ready 输出

Ready 的内部判断是 Harness Gate（控制门），但默认用户只看到需求简报。

默认用户可见模板：

```markdown
## 需求简报
问题：
- ...

用户：
- ...

场景：
- ...

第一版主动作：
- ...

数据行为：
- ...

不做事项：
- ...

验收标准：
- ...
```

内部控制结构：

```markdown
## 内部 Harness Gate（不默认展示给用户）
### 必须实现
- ...

### 不得实现
- ...

### 允许假设
- ...

### 禁止假设
- ...

### 验收标准
- ...
```

按需输出的执行 Prompt：

```markdown
## 执行 Prompt
你要实现一个小应用。只能实现下面确认过的内容，不要添加任何未确认功能。

问题：
- ...

用户：
- ...

核心流程：
- ...

数据行为：
- ...

必须实现：
- ...

不得实现：
- ...

禁止假设：
- ...

验收标准：
- ...
```

规则：

- 只有七个门槛全部确认后，才能展示需求简报。
- 默认 Ready 输出不得展示 Harness Gate 和执行 Prompt。
- 需求简报不能包含未确认功能。
- 执行 Prompt 必须由内部 Harness Gate 生成。
- 用户明确要求生成执行 Prompt 时，才追加执行 Prompt。
- 用户未明确要求实现时，不主动把对话推进到 coding agent。

## 执行 Prompt 按需输出触发条件

满足以下任一条件时，可以在需求简报后追加执行 Prompt：

- 用户说“生成执行 Prompt”。
- 用户说“给我可以交给 Codex/Claude Code/Cursor 的 prompt”。
- 用户说“下一步让 AI 实现”。
- 用户明确要求“开始写代码”或“交给下一个 agent 做”。

如果用户只是确认需求，例如“看起来可以”“就这样”，默认只输出需求简报，不输出执行 Prompt。

## Harness Gate（控制门）语义

Harness Gate 是内部控制结构，不默认暴露给用户。

### 必须实现

这里只能放用户已经确认的第一版行为。

### 不得实现

这里放已确认不做的内容，以及最容易过度发挥的内容。

### 允许假设

允许假设必须低风险，并且不决定技术架构，例如：

- 使用清楚的按钮和标签。
- 界面保持简单。
- 空状态有基本提示。

不得允许这些假设：

- 添加登录。
- 把数据存在云端。
- 添加 AI 推荐。
- 添加统计分析或报表。

### 禁止假设

这是硬边界。内部 Harness Gate 和按需生成的执行 Prompt 必须明确禁止所有用户没有确认、但编程 agent 可能想添加的功能。

## 示例流程

输入：

```text
我想做一个学习管理网站。
```

第一轮不应该问技术栈、登录、数据库或完整功能列表。

应该问：

```markdown
## 已确认
- 你想做一个学习管理相关的网站。

## 下一步
“学习管理网站”还不是一个清楚的问题。你现在最想先摆脱哪种学习上的麻烦？

A. 每天不知道该先学什么
B. 作业或截止日期容易忘
C. 资料和笔记太乱
D. 学了多久、有没有坚持不清楚

推荐：先选 A。它最容易收成一个很小的第一版：打开后只处理今天该做什么。
```

## 测试策略

冒烟测试应覆盖：

1. 模糊想法必须保持 `Need More Info`，并优先追问问题 / 痛点。
2. 用户说“都要”时，必须要求确认第一版优先级。
3. 用户说“你决定”时，必须要求确认推荐方案。
4. 七个门槛都确认后，才能输出 `Ready`。
5. 默认 Ready 用户可见输出只包含需求简报。
6. 内部 Ready 判断必须经过 Harness Gate（控制门）。
7. 用户明确要求后，才输出执行 Prompt。
8. 除非用户确认，否则需求简报和执行 Prompt 都不得引入登录、后端、支付、AI、统计或同步。
