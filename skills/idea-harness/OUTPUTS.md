# 输出模板

SKILL.md 的核心循环判定状态后，按本文件的模板输出。

## 输出层次

- **用户层**：用户直接看到的内容。保持极简。
- **内部层**：skill 内部维护的控制结构。默认不展示。

## gathering / needs-precision / blocked → Need More Info

```markdown
## 已确认
- ...（1-3 条，用用户的语言复述）

## 追问
（可选铺垫：复述原话、指出矛盾、或描述场景）

（一个问题，从六种问法中选最合适的）
```

默认是开放性问题，不给选项。只有当问题对应明确的取舍分叉时才列选项：

```markdown
A. ...
B. ...

推荐 X，因为你说过"..."
```

推荐理由只在给出选项时出现，且必须引用用户说过的话。

英文标题：Confirmed / Question / Recommended。

### 各状态特别规则

- **gathering**：追问指向下一个最重要的未回答门槛（按决策树优先级）。
- **needs-precision**：追问指向精确度缺口，不是新门槛。优先使用"假设暴露""场景走查""对比锚定"三种问法。
- **blocked**：
  - 冲突 → 把两句原话并排引出来，只问"哪个是你真正想要的"。
  - "都要" → 构造代价场景，然后只问 V1 先做哪个。
  - "你决定" → 给推荐 + 用用户场景解释 + 等确认。

## ready → 需求简报

```markdown
## 需求简报
问题：
- ...

用户：
- ...

场景：
- ...

第一版主动作：
- ...

数据行为：
- ...

不做事项：
- ... — <原因，引用用户的话或已确认的范围决策>
- ... — <原因>

验收标准：
- ...
```

英文标题对应翻译（Requirements Brief / Problem / User / Scenario / V1 main action / Data behavior / Non-goals / Acceptance criteria）。

### 不做事项规则

- 每条必须附带原因。原因来自用户的回答或范围决策。
- 需求简报的不做事项是所有边界的唯一源头。执行 Prompt 的 `不得实现` 只能复制或泛化这些边界，不能新增具名功能。
- 默认阻止列表中与当前想法高度相关的项目，必须在 Ready 前追问用户是否需要，或写入不做事项并附带范围原因。

### 验收标准规则

- 每条必须是可检查的动作或可见结果，推荐格式"当/如果 ...，用户能看到/完成 ..."。
- 每个主动作至少对应一条验收标准；多个管理动作（搜索、编辑、删除）必须逐项拆开。
- 涉及保存时，写清保存后的可见结果；涉及重新打开、换设备、同步时，写清检查场景。
- 涉及账号、权限、多用户时，必须包含正向标准和反向标准。
- 涉及搜索、筛选、排序时，写清输入、结果包含什么、不包含什么。
- 只能写"能记录""能搜索"这类泛句 = 还没有 Ready，继续追问。

### 需求简报总则

- 只写用户明确说过或确认过的内容。
- 不得补登录、后端、支付、AI、统计、同步、分享或其他默认假设。
- Ready 输出默认不展示执行 Prompt。

## 执行 Prompt（按需输出）

只有门槛全部确认 + 精确度检查全通过 + 用户明确要求时，才输出。

触发语："生成执行 Prompt" / "generate an execution prompt" / "给我可以交给 Codex/Claude Code/Cursor 的 prompt" / "交给下一个 agent 做"。

如果用户只是说"看起来可以""就这样"，只展示需求简报。门槛未全部确认时继续澄清，不输出。

### 行为契约风格

描述行为，不描述 UI 元素。不写"有一个按钮"，写"用户可以执行某动作"。

```markdown
## 执行 Prompt
你要实现一个小应用。只能实现下面确认过的内容，不要添加任何未确认功能。

当前痛点：
- ...

期望行为：
- ...（用户视角的完整使用流程，描述行为而非 UI 元素）

数据行为：
- ...

必须实现：
- ...

不得实现：
- ... — <原因，复制需求简报的不做事项>

禁止假设：
- 不要添加任何上面没有确认的功能。
- 不要实现 `不得实现` 中列出的事项。

验收标准：
- ...（复制需求简报的验收标准，不新增）
```

英文时整段翻译，结构不变。

### 可选：任务切片

只有用户问"怎么拆任务""分步骤做"时才输出。

```markdown
## 任务切片
### V1 必须
- ...

### 需要用户决策
- ...

### 可直接实现
- ...
```

## 原型逃生口

连续追问后用户对视觉或流程仍然模糊时，不继续文字追问，建议低保真原型：

```markdown
我们在文字上可能很难继续推进了。建议先做一个只回答一个问题的低保真原型。

你最想先看到的是哪个？
A. 主界面长什么样（UI 原型）
B. 从头到尾的操作流程（流程原型）
```

原型建议不改变状态机状态，是辅助手段。
